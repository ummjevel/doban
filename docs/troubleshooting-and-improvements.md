# 도반 트러블슈팅 및 개선 기록

서비스 소개서와 발표자료에 넣기 위한 시행착오/개선 내용 정리.

## 요약

도반은 한국관광공사 OpenAPI를 활용해 관광 데이터를 창업 관점으로 해석하는 챗봇이다. 테스트 과정에서 가장 큰 문제는 API 호출 자체보다 **지역코드 매핑**, **최신 기준월 선택**, **중간 로그 노출**, **지표 해석 과장**이었다.

개선 방향은 다음 네 가지로 정리된다.

- 관광지명/상권명을 주소와 행정구역으로 변환한 뒤 데이터랩 API용 코드로 매핑
- 현재 날짜 기준 최신 조회 가능월과 최근 6개월 추이를 우선 사용
- API 재시도 과정과 내부 로그를 최종 답변에서 제거
- 관광 지표를 창업 판단의 참고 신호로만 해석하고, 매출/소비 행태는 단정하지 않음

## 1. 지역코드 매핑 오류

### 문제

사용자는 보통 `전주 한옥마을`, `해운대`, `구룡포`처럼 관광지명이나 상권명으로 질문한다. 하지만 데이터랩 계열 API는 `areaCd`, `signguCd` 같은 행정구역 코드를 요구한다.

초기 테스트에서는 모델이 지역코드를 추측하거나 여러 코드를 재시도하는 과정이 답변에 그대로 노출됐다.

```text
전주시 기준으로 지역코드 37, 시군구코드 37011을 사용합니다.
전북 전주시 완산구 기준으로 지역코드 34, 시군구코드 34011로 재조회합니다.
찾았어요! 전주시 완산구: 지역코드 52, 시군구코드 111이네요.
```

### 원인

- 관광지명과 행정구역명이 항상 일치하지 않음
- 국문 관광정보 서비스 코드와 데이터랩 계열 API 코드 체계가 다를 수 있음
- 기존 코드 CSV가 행정구역명 중심이라 관광지명 입력을 바로 처리하기 어려움
- 모델이 확인되지 않은 코드를 추측하려는 경향이 있음

### 개선

- 지역/시군구 코드 파일을 엔노이아 문서 폴더 규칙에 맞게 CSV로 정제
  - `region_name_lookup_rag.csv`
  - `area_codes_rag.csv`
  - `region_codes_rag.csv`
  - `indicator_codes_rag.csv`
- 자주 쓰는 관광지명 보정 파일 추가
  - `place_region_overrides_rag.csv`
  - 예: `전주 한옥마을 -> 전북특별자치도 전주시 완산구 -> areaCd=52, signguCd=52111`
- 국문 관광정보 서비스 `KorService2 /searchKeyword2`를 추가해 장소명으로 주소를 먼저 확인
- 시스템 프롬프트에 지역코드 추측 금지 규칙 추가

### 개선 후 흐름

```text
사용자 질문
-> 장소명/지역명 추출
-> 장소명이면 searchKeyword2로 주소 확인
-> 주소에서 시도/시군구 확인
-> CSV/RAG에서 데이터랩용 areaCd, signguCd 매핑
-> 데이터랩 계열 API 호출
-> 미니 컨설팅 리포트 생성
```

### 효과

- 잘못된 지역코드 호출 감소
- 지역코드 재시도 로그 노출 감소
- 관광지명 기반 질문 처리 가능
- API별 코드 체계 혼동 감소

## 2. 최신 기준월 선택 문제

### 문제

초기 테스트에서는 `202410`처럼 과거 기준월이 고정되어 사용됐다. 창업 판단은 “최근에도 수요가 있는가”가 중요하기 때문에 오래된 단일월 데이터만으로는 충분하지 않았다.

### 원인

- API 테스트 기본값이 분석 기준에 그대로 남음
- API마다 제공 가능한 최신월이 다를 수 있음
- 현재월 데이터는 집계가 완료되지 않았을 가능성이 있음
- 단일월만 보면 계절성이나 일시적 변동을 구분하기 어려움

### 개선

시스템 프롬프트에 기준연월 선택 규칙을 추가했다.

```text
- current_date를 우선 사용
- 현재월은 기본 분석에서 제외
- 현재월 기준 2개월 전부터 최신 후보월 탐색
- API별 최대 6개 후보월까지만 조회
- 조회 가능한 최신 baseYm을 사용
- 같은 세션에서 확인한 최신 성공월은 재사용
- 일반 분석은 최근 6개월 추이를 우선 사용
- 상세 분석 요청 시에만 12개월 추이 사용
```

엔노이아 플로우에서 권장하는 변수:

```text
current_date = 2026-06-05
current_month = 202606
candidate_baseYm = 202604, 202603, 202602, 202601, 202512, 202511
latest_baseYm_by_api = API별 최신 성공월
```

### 효과

- 최신성 있는 분석 가능
- 단일월 지표에 과도하게 의존하는 문제 감소
- 최근 3~6개월 흐름과 계절성 힌트 제공
- 같은 최신월 탐색을 반복하지 않아 API 호출 수 감소

## 3. API 호출 로그와 중간 메시지 노출

### 문제

API 호출 전후 안내 문장이 최종 답변 앞에 이어붙어 보였다. 특히 엔노이아 화면에서는 중간 진행 메시지가 별도 카드가 아니라 일반 텍스트로 누적되어 시연 완성도가 떨어졌다.

예시:

```text
관광 서비스 수요와 중심관광지를 함께 조회합니다.
세부 지표와 최근 6개월 추이를 추가로 조회합니다.
식음료 소비액 6개월 추이를 조회합니다.
데이터가 확보되었습니다.
```

춘천 테스트에서는 지역코드 재시도 로그도 노출됐다.

```text
시군구 코드를 재확인합니다. 춘천시의 코드를 다르게 시도합니다.
강원 광역코드로 2024년 하반기 데이터를 시도합니다.
코드 확인: areaCd=51, signguCd=51110입니다.
```

### 원인

- 도구 호출 과정과 최종 답변 생성 과정이 분리되지 않음
- 모델이 진행 상황을 친절하게 설명하려는 경향이 있음
- 엔노이아에서 중간 출력이 카드 UI가 아니라 일반 텍스트로 표시됨

### 개선

시스템 프롬프트에 아래 규칙을 추가했다.

```text
- 최종 답변은 리포트 제목, 결론, 확인 질문으로 바로 시작
- "조회합니다", "확인됩니다", "데이터가 확보되었습니다" 같은 문장 금지
- 지역코드는 "분석 기준"에만 표시
- 잘못된 코드 후보나 재시도 과정은 출력하지 않음
- 실패한 API는 반복 재시도하지 않고, 누락 데이터로 짧게 요약
```

API 호출 예산도 함께 제한했다.

```text
- 기본 분석은 4~6회 이내 호출 목표
- 장소 확인은 searchKeyword2 1회
- 최신월 탐색은 API별 최대 6개 후보월
- 추이 분석은 핵심 지표 API 1~2개에 한정
```

상태 카드 방식도 검토했지만 엔노이아에서는 일반 텍스트로만 표시되어 제외했다. 중간 메시지가 불가피하면 아래처럼 한 문장만 허용한다.

```text
자료를 확인하고 있습니다.
```

### 효과

- 답변 첫머리가 더 깔끔해짐
- 시연 화면에서 내부 처리 과정 노출 감소
- API 호출량과 응답 지연 감소
- 사용자가 기술 로그보다 창업 판단에 집중 가능

## 4. 후속 질문 답변이 너무 긴 문제

### 문제

사용자가 이미 분석한 지역에 대해 `2026년 동향 알려줘`, `최근에는 어때?`처럼 후속 질문을 하면 전체 미니 컨설팅 리포트를 다시 출력하는 경향이 있었다.

### 원인

- 기본 답변 구조가 항상 전체 리포트로 고정되어 있었음
- 최초 질문과 후속 질문을 구분하는 규칙이 부족했음
- 사용자는 변화만 알고 싶은데 추천 아이템과 추가 확인사항까지 반복됨

### 개선

후속 질문 전용 구조를 추가했다.

```text
## 도반 업데이트 리포트

### 1. 핵심 변화
### 2. 전년 또는 이전 기간 비교
### 3. 창업 판단에 주는 의미
### 4. 추가 확인사항
```

추가 규칙:

- 후속 질문에서는 추천 아이템을 다시 나열하지 않음
- 사용자가 요청한 경우에만 추천 아이템 갱신
- 전체 리포트 대신 변화 중심으로 짧게 답변

### 효과

- 후속 대화가 자연스러워짐
- 토큰 사용량 감소
- 사용자가 원하는 최신 변화에 집중 가능

## 5. 지표 해석 과장 문제

### 문제

초기 답변에서 API 지표를 `100점 만점`, `전국 평균`, `중상위권`처럼 해석하거나, 소비액/검색량/SNS 지표만으로 소비 행태를 단정하는 표현이 나왔다.

예시:

```text
검색·관심은 높고, 지갑은 덜 열리는 구조가 심화됐습니다.
저단가 소비로 이동했을 가능성이 있습니다.
고객 1인당 지출이 줄어드는 국면에서 회전율 중심 운영이 유리합니다.
전주와 구룡포가 유사하므로 광역적 소비 위축 가능성이 있습니다.
```

### 원인

- API 문서에서 지표값의 기준이 명확히 확인되지 않은 상태였음
- 모델이 숫자 지표를 점수나 순위처럼 해석하려는 경향이 있음
- 검색량과 소비액이 엇갈릴 때 원인을 설명하려고 소비 행태를 추정함

### 개선

시스템 프롬프트에 금지 표현과 보수적 해석 규칙을 추가했다.

```text
- 기준이 확인되지 않은 지표값은 "상대적 크기를 보여주는 참고 지표"라고 설명
- 100점 만점, 전국 평균, 상위권/하위권 표현 금지
- 매출, 방문자 규모, 임대료, 객단가를 만들어내지 않음
- "지갑이 덜 열렸다", "저단가 소비로 이동했다", "광역적 소비 위축" 같은 단정 금지
- 두 지역 사례만으로 전국적/광역적 흐름을 일반화하지 않음
- 소비 행태 해석은 가능성/가설/추가 검증 필요로 표현
```

개선 후 표현 예시:

```text
내비게이션 음식 검색량은 보합이지만 식음료 소비액 지표는 하락했습니다.
이는 방문 전 관심 또는 목적지 검색 신호가 유지되는 반면, 소비 지표는 약해졌을 가능성을 보여줍니다.
다만 이 API만으로 객단가 하락, 포장 소비 증가, 고단가 식사 감소를 확인할 수는 없습니다.
메뉴 가격대와 운영 방식은 카드매출, 배달앱, 네이버 플레이스, 현장 방문 자료로 교차 확인하는 것이 좋습니다.
```

### 효과

- 공공데이터 기반 서비스로서 신뢰성 향상
- 창업 성공이나 매출을 과장하지 않음
- 데이터로 확인된 사실과 해석 가설을 구분
- 실제 창업 판단에 필요한 추가 확인사항을 함께 안내

## 6. 최종 개선된 답변 원칙

도반의 최종 답변은 아래 원칙을 따른다.

- 지역명/관광지명은 먼저 행정구역으로 확인
- 확인된 코드가 없으면 API 호출보다 사용자 확인 질문 우선
- 최신 조회 가능월과 최근 6개월 추이를 우선 사용
- 중간 API 로그는 출력하지 않음
- 답변은 미니 컨설팅 리포트 또는 업데이트 리포트로 구조화
- 데이터 근거, 해석, 한계를 구분
- 매출, 임대료, 객단가, 창업 성공은 보장하지 않음
- 현장조사, 카드매출, 배달앱, 네이버 플레이스 등 외부 검증 필요성을 안내

## PPT에 넣기 좋은 1장 요약

```text
시행착오
- 관광지명 입력 시 데이터랩 지역코드를 잘못 추측하는 문제가 있었다.
- 오래된 기준월로 조회되어 최신 창업 판단에 한계가 있었다.
- API 호출 과정과 재시도 로그가 사용자 답변 앞에 노출됐다.
- 지표값만으로 소비 행태나 창업 전략을 과하게 해석하는 문제가 있었다.

개선
- 국문 관광정보 API와 정제 CSV를 조합해 장소명 -> 주소 -> 데이터랩 코드로 매핑했다.
- current_date 기준 최신 조회 가능월과 최근 6개월 추이를 사용하도록 프롬프트를 보강했다.
- API 호출 예산과 로그 출력 금지 규칙을 추가했다.
- 후속 질문은 업데이트 리포트로 짧게 답하도록 구조를 분리했다.
- 소비 행태는 단정하지 않고 가능성/가설/추가 검증 필요로 표현하도록 수정했다.

효과
- 지역 매핑 정확도와 답변 안정성이 개선됐다.
- 시연 화면에서 내부 처리 로그 노출을 줄일 수 있다.
- 공공데이터 기반 창업 분석 서비스로서 신뢰성과 차별성이 높아졌다.
```
